[02:00] Agent Stack Release-Auslesung: Hermes Agent v0.22.2, v0.22.1, v0.22.0, v0.21.7

Hermes Agent v0.22.2 wurde am 15. Oktober 2026 veröffentlicht, und es ist das Release, das v0.22.1 hätte sein sollen. Am Tag davor wurde v0.22.1 aus dem falschen Commit erstellt, was bedeutet, dass es unveröffentlichte Gateway-Arbeit enthielt und die Microsoft Store-Version auf einem „Verbinden"-Bildschirm hängen bleiben konnte. 0.22.2 macht diesen Fehler rückgängig und liefert stattdessen zwei Fixes.

Der größere der beiden ist ein Neustart-Bug. Unter Linux kann der Kernel nach einem Neustart eine frühe PID vergeben, die dann einem völlig unrelated Prozess gehört, der zuerst hochgefahren ist. Das überwachte Gateway – systemd, launchd, Docker – würde dann einen laufenden Gateway sehen und sich weigern zu starten. Hermes zeichnet nun auf, in welchem Boot es gestartet wurde, und wenn es das nicht feststellen kann, fragt es das Host-Lock ab, das nur ein aktiver Gateway tatsächlich hält.

Der andere ist eine Überarbeitung der Laptop-Ergonomie für lokale Modelle. Lokale Anfragen streamen jetzt immer den Prompt-Lesefortschritt in der Statusleiste, sodass Sie sehen können, wie weit der Server bei einem langen Prompt gekommen ist. Stall-Timer überspringen die Zeit, in der der Laptop im Schlafmodus war, sodass eine schlafende Konversation nicht als stagnierend erscheint. Ein wiederhergestellter lokaler Server erhält einen weiteren Retry anstatt eines Circuit Breakers, der jeden späteren Turn fehlschlagen lässt. Kompression löst kein Timeout mehr, während der Server noch eine lange Konversation liest. Bei Windows-Maschinen mit unified Memory werden Modell-Launch und Prompt-Cache so dimensioniert, dass Speicher freigegeben wird, was wichtig ist, wenn es keinen separaten VRAM-Pool gibt.

Ein Vorbehalt, den das Projekt anspricht: Sitzungen, die unter dem 0.22.1-Gateway liefen, können in 0.22.2 nicht gelöscht werden. Alles, das sauber unter dem richtigen Build gestartet wurde, kann gelöscht werden; nur die schlechten Build-Sitzungen sind festgefahren.

Kontext zur Zeile: v0.22.0 erschien am 13. Oktober als „Threshold Release" und wurde vom Projekt als das größte Fenster beschrieben, das Hermes je ausgeliefert hat, etwa 2,5x des v0.21.0-Zyklus. Die Hauptneuerungen waren ein geführter Ersteinrichtungs-Chat, der auf einem kostenlosen Testmodell läuft, sodass Neulinge keinen API-Schlüssel benötigen, um zu starten, Konnektoren, die den Agenten in gehostete Apps bringen, eine One-Click-llama.cpp-Runtime für lokale Modelle und signierte Desktop-Pakete einschließlich des Microsoft Store-Builds.

Für Builder ist dies mostly ein Stabilitäts-Update. Wenn sich Ihr überwachtes Gateway nach einem Server-Neustart geweigert hat zu starten oder Ihre Store-App beim Verbinden eingefroren ist, ist dieses Update der Fix. Lokale-Modell-Bastler, besonders auf Windows-unified-Memory-Laptops, erhalten ein ruhigeres Erlebnis bei langen Konversationen und Laptop-Schlafphasen.

[04:38] Apple MLX Führt Nahezu-Billion-Parameter Muse Spark Open auf Mac Studio Cluster Aus

Apples ML-Forschungsgruppe hat einen praxisorientierten Leitfaden für die Ausführung von Frontier-Scale-Sprachmodellen vollständig auf Mac Studio-Hardware mit MLX, ihrem Open-Source-Array-Framework, veröffentlicht. Das Hauptergebnis: Ein nahezu eine Billion Parameter großes Mixture-of-Experts-Modell namens Muse Spark Open generiert über 36 Tokens pro Sekunde, wenn es auf vier Mac Studios mit M5 Ultra-Chips verteilt ist, weit über der durchschnittlichen Lesegeschwindigkeit.

Auf einem einzelnen M5 Ultra Mac Studio mit 512 GB unified Memory passen Mistral Medium 3.5 (128 Milliarden Parameter) und Qwen 3.8 (27 Milliarden Parameter) bequem. Die M5-Generation fügt einen GPU Neural Accelerator hinzu, der für Matrixmultiplikation dediziert ist, was sich in bis zu 4,6× schnellerer Time-to-First-Token im Vergleich zum M3 Ultra niederschlägt. Die Decodiergeschwindigkeit, die durch die Speicherbandbreite begrenzt ist, verbessert sich um etwa 1,6× dank der 1,2 TB/s unified Memory-Bandbreite des M5 Ultra, hoch von 819 GB/s beim M3 Ultra. Die Spitzenleistung bleibt bei etwa 300 Watt, ungefähr das, was ein Toaster zieht.

Muse Spark Open mit 816 Milliarden Gesamtdparametern und 42 Milliarden aktiven pro Token benötigt roughly 493 GB in NVFP4-Quantisierung, zu groß für eine Maschine. MLX v0.30.1 und später, gepaart mit dem latenzarmen RDMA-over-Thunderbolt 5 Treiber von macOS 26.2, verteilt das Modell auf mehrere Macs unter Verwendung neuer Kommunikations-Collectives namens jaccl. MLX unterstützt zwei Ansätze: Pipeline-Parallelität, die das Modell über die Tiefe aufteilt (ein Mac führt die erste Hälfte der Schichten aus und übergibt dann die Ergebnisse an den zweiten), und Tensor-Parallelität, die über die Breite aufteilt. Ein Hilfsbefehl, mlx.launch, macht es einfach, Jobs über mehrere Hosts über eine Thunderbolt-verbundene Paarung zu starten.

Für Builder bedeutet der Workflow, dass große Modelle lokal auf Büro-Hardware bleiben können und privates agentisches Coding und andere kontextintensive Workloads ohne Cloud-Unterstützung ermöglichen.

[07:37] MiniCPM-V 4.7 Erhält Geschwindigkeitsboost durch Spekulatives Decoding

OpenBMB hat einen GGUF-quantisierten DSpark-Draft-Checkpoint für MiniCPM-V 4.7 auf Hugging Face veröffentlicht, der spekulatives Decoding mit llama.cpp ermöglicht. MiniCPM-V ist eine Familie von offenen Vision-Language-Modellen, die für On-Device- und Edge-Deployment konzipiert wurden, und dieses Repository ermöglicht die Ausführung mit llama.cpp spekulativem Decoding. Spekulatives Decoding kombiniert ein kleines Draft-Modell, das mehrere Token vorhersagt, mit einem größeren Target-Modell, das diese Vorhersagen parallel verifiziert. Anstatt auf das vollständige 35-Milliarden-Parameter-Modell zu warten, das ein Token nach dem anderen generiert, schlägt der Draft eine Batch vor, die das Target bestätigt oder verwirft, was die sichtbare Ausgaberate beschleunigt. Der Draft hat etwa 389 Millionen Parameter und sagt 15 Token pro Forward-Pass voraus, mit Fokus auf bestimmten Hidden-State-Schichten im Basismodell. Evaluationsergebnisse zeigen Akzeptanzlängen von etwa 3,5 Token pro Verifizierungsrunde bei allgemeinem Text bis zu 7,4 bei Code-Aufgaben, mit Vision-Benchmarks wie MMMU und MathVista bei etwa 5 bis 6 akzeptierten Token. Zur Verwendung lade das Target-Modell, seinen Vision-Projector und den quantisierten Draft herunter, und führe ihn dann mit dem Draft-DSpark-Spec-Typ in llama-cli aus oder starte ihn als Multimodal-Server. Der Draft muss mit dem passenden MiniCPM-V 4.7 35B-A3B Target gepaart werden, und er erfordert einen llama.cpp-Build, der die dflash-Architektur und den DSpark-Markov-Head unterstützt. Die Quantisierung des Drafts selbst beeinflusst nur, wie oft Vorhersagen akzeptiert werden, niemals das Endergebnis, sodass Entwickler den kleinsten quantisierten Draft verwenden können, der in ihren Speicher passt. Das Draft-Modell sagt 15 Token pro Forward-Pass voraus, und Benchmarks zeigen vom Herausgeber gemeldete Durchschnittswerte von 3,501 akzeptierten Token pro Verifizierungsschritt bei allgemeinem Text und 7,387 bei der Code-Generierung. Der quantisierte Draft läuft mit llama-cli oder llama-server unter Verwendung des Flags --spec-type draft-dspark, was einen llama.cpp-Build mit dflash-Architektur erfordert.

Dies ist wichtig für lokale Inferenz, da spekulative Dekodierung den Durchsatz sogar auf bescheidener Hardware verbessern kann, da der Draft die anfängliche Token-Vorhersage übernimmt und das Ziel ihn bestätigt oder korrigiert. Entwickler, die llama-cli oder llama-server ausführen, können GPU-Offloading für sowohl Ziel als auch Draft auf Maximum konfigurieren, eine Kontextlänge von 8192 einstellen und das Q4_K_M-Ziel mit einem Q8_0-Draft kombinieren, um die Speichernutzung niedrig zu halten. Der Draft muss mit dem passenden MiniCPM-V 4.7 1B-Ziel gepaart werden; er erfordert llama.cpp mit der dflash-Architektur und dem DSpark-Markov-Head. Ein neues Hugging-Face-Repository veröffentlichte den GGUF-quantisierten DSpark-Draft-Checkpoint für MiniCPM-V-4.7-1B und ermöglicht spekulative Dekodierung durch llama.cpp. Der DSpark-Draft generiert 15 Kandidaten-Tokens pro Forward-Pass über 5 Draft-Schichten, die das Zielmodell verifiziert, um die Inferenz zu beschleunigen.

[21:16] GitHub Copilot stellt mehrere Modelle am 16. November ein

GitHub postede am 15. Oktober einen Änderungsprotokoll, das ankündigte, dass eine Reihe von GitHub Copilot-Modellen am 16. November 2026 eingestellt wird. Die Einstellung gilt für jede Copilot-Oberfläche: Copilot Chat, Inline-Bearbeitungen, Ask-Modus, Agent-Modus und Code-Vorschläge. Der praktische Effekt ist, dass jeder Benutzer, der ein demnächst einzustellendes Modell in seinen Copilot-Einstellungen angepinnt hat, sehen wird, wie es am Stichtag nicht mehr funktioniert. Code-Vervollständigungen, Chats und Agent-Läufe, die auf einem der betroffenen Modelle basierten, werden nach diesem Tag ein neues Standardmodell benötigen. Die vollständige Liste der betroffenen Modelle befindet sich im GitHub-Änderungsprotokoll-Post selbst, zusammen mit eventuell vorgeschlagenen Ersatzmodellen. Die Einstellung betrifft Copilot Chat, Ask-Modus, Agent-Modus, Inline-Bearbeitungen und Code-Vervollständigungen am selben Tag, sodass ein Copilot-Benutzer, der mitten in einer Sitzung von Inline-Vervollständigung zu Chat wechselt, sich nicht retten wird, indem er die Oberflächen wechselt. Jeder, dessen Team einen bestimmten Modellaufruf hinter einem Copilot-Plan standardisiert hat, wird bestätigen wollen, dass diese Wahl noch auf der unterstützten Liste steht, bevor November beginnt.
